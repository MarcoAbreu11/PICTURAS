# Upload benchmark results

Non-functional requirement: **performance efficiency / resource utilisation
when uploading large files** (ISO/IEC 25010:2011). Baseline and final version
measured on the same machine, with the same scripts, the same services and the
same Compose overrides. Raw data: `results/*.csv` (one row per upload).

### Stack configuration (identical for both versions)

- Services: `nginx frontend api_gateway ws_gateway seaweedfs img_storage
  rabbitmq projects projects_mongoDB users users_mongoDB subscriptions
  subscriptions_mongoDB brightness_tool video_tool`.
- `compose.memlimit.yaml`: `mem_limit: 1g` and `memswap_limit: 1g` (no swap)
  for `api_gateway`, `projects` and `img_storage`. Without the swap limit the
  kernel could move the buffered file to swap, which would lower the measured
  RSS of the baseline.
- A local port override (not versioned) published the SeaweedFS filer on host
  port 19090 instead of 9090, which another service on this host uses. The
  upload path does not use that port.
- Each version ran under its own Compose project name (`picturasbench-base`,
  `picturasbench-final`), so both started from empty volumes.
- The baseline tree was extracted with `git archive 0523102`, plus a copy of
  `bench/upload/` from the final commit, since the scripts did not exist yet.
  Its CSV `commit` column was set to `0523102` afterwards, because the
  extracted tree has no `.git`.
- Samples generated by `make_samples.sh` inside the `video_tool` image
  (ffmpeg with libx264): 105 143 130, 525 712 361 and 998 459 595 bytes.

### Commands (run once per version, `--label baseline` / `--label final`)

```bash
export COMPOSE_FILE=docker-compose.yaml:bench/upload/compose.memlimit.yaml   # + local overrides, if any
docker compose up -d --build <services above>
python3 bench/upload/regression.py

python3 bench/upload/measure_upload.py --label <label> --sizes 100 --reps 3 --concurrency 4

```

## Results

Memory growth: the peak resident memory (VmRSS) of a service's Node
processes during the upload, minus the value just before it. The table shows
the median and maximum over the repetitions. "Path total" is the median of the
sum over the three services.

| version | file | concurrent | uploads accepted | api_gateway med/max MB | projects med/max MB | img_storage med/max MB | path total med MB | time med s |
|---|---|---|---|---|---|---|---|---|
| baseline | 100 MB | 1 | 5/5 | 332 / 405 | 210 / 210 | 206 / 207 | 749 | 2.0 |
| final | 100 MB | 1 | 5/5 | 20 / 26 | 28 / 31 | 59 / 61 | 105 | 1.5 |
| baseline | 500 MB | 1 | **0/5** | 856 / 934 * | 2 / 2 | 0 / 0 | 858 * | 2.3 † |
| final | 500 MB | 1 | 5/5 | 47 / 48 | 74 / 75 | 77 / 86 | 193 | 6.5 |
| baseline | 950 MB | 1 | **0/5** | 839 / 898 * | 2 / 3 | 0 / 0 | 841 * | 5.8 † |
| final | 950 MB | 1 | 5/5 | 47 / 47 | 75 / 78 | 100 / 105 | 220 | 11.8 |
| baseline | 4 × 100 MB | 4 | **0/12** | 801 / 812 * | 8 / 59 | 0 / 0 | 818 * | 1.5 † |
| final | 4 × 100 MB | 4 | 12/12 | 74 / 74 | 77 / 82 | 143 / 146 | 296 | 3.5 |

\* Lower bound. The gateway's Node process was killed when its container
reached the 1 GB limit (`OOMKilled=true`; nodemon logged `app crashed` once per
failed run: 10 serial runs and 3 concurrent runs, 13 in total). The sampler, which reads every 0.25 s,
missed the last moments before the kill.
† Time until nginx answered `502 Bad Gateway` after the gateway died, not an
upload time. The file never reached `projects` or `img_storage`, which is why
their growth is about zero.

Regression checks (`regression.py`): **19/19 pass on both versions**. They
cover accepted uploads, byte-identical download, metadata, the existing
rejections, the 401 response without a token and a pipeline over an image and a
video.

### Reading the numbers

- **Baseline.** Each service on the path holds the whole file in memory.
  Per 100 MB file, the growth was about 3.3× the file in `api_gateway` (multer
  buffer, a new `FormData`, and the copy axios keeps while redirects are
  enabled) and about 2× in `projects` and `img_storage`. The path total was
  about 7.5× the file. Under a 1 GB budget per service, the baseline accepted
  no file of 500 MB or more and no batch of 4 × 100 MB uploads.
- **Final.** Memory growth no longer follows the file size. From 100 MB to
  950 MB (9.5× more data), the largest per-service growth went from 61 to
  105 MB. `img_storage` still grows somewhat with the file size (59 → 77 →
  100 MB median). That memory is freed after the upload; the measurement does
  not separate garbage-collector lag from live data. With 4 concurrent uploads
  the maximum was 146 MB, in `img_storage`.
- **Time.** Only the 100 MB serial case is comparable, because the baseline
  fails at every other point: the median went from 2.0 s to 1.5 s (−25%).
  Throughput of the final version: about 70 MB/s at 100 MB, 81 MB/s at
  500 MB and 85 MB/s at 950 MB.
- **nginx timeout.** The baseline uses nginx's default `proxy_read_timeout`
  of 60 s on `/api-gateway/`; the final version sets 300 s. On this machine
  the timeout did not decide any result. The baseline failed through OOM after
  at most about 6 s, and the slowest final upload took 14.1 s. On slower
  hosts without memory limits, the baseline fails with `504` after about 60 s
  instead.
- **Container memory (`*_cgroup_peak_mb`, context only).** `docker stats`
  also counts page cache, and its slow sampling misses short peaks. For the
  final version, `projects` reached up to 578 MB with the 950 MB file because
  of the page cache of its temporary file. The kernel reclaims that cache
  under pressure, which is why the 1 GB limit never killed it.

## Quantification

| Item | Value |
| --- | --- |
| Scale | Memory growth of each service on the upload path (`api_gateway`, `projects`, `img_storage`), in MB: peak VmRSS during the upload minus the value just before it |
| Method | `measure_upload.py`, VmRSS sampled every 0.25 s; 100, 500 and 950 MB files, 5 uploads each, plus 3 runs of 4 concurrent 100 MB uploads; 1 GB limit without swap per service; maximum over the repetitions |
| Baseline | 405 MB maximum, 332 MB median (`api_gateway`, 100 MB file, about 3.3× the file); no file of 500 MB or more accepted (OOM) |
| Target | ≤ 150 MB per service at every tested size and with 4 concurrent uploads, and every upload up to 950 MB accepted |
| Minimum acceptable | ≤ 25% of the file size per service for files of 500 MB or more, and every upload up to 950 MB accepted |
| Time | Median upload time at most 10% above the baseline where both versions succeed (100 MB, serial) |

Why these values: the target is a fixed number because memory must stop
following the file size; 150 MB leaves room for the stream buffers, the two
5 MB S3 parts in flight and garbage-collector lag, and is well under the 1 GB
budget. The minimum is relative to the file so that it still rules out any
service holding the whole file (the baseline held 200–330% of it). It is
applied from 500 MB because at 100 MB the fixed overhead dominates: the final
version grows 61 MB there (61% of the file) while being 6.6× below the
baseline. Time only compares 100 MB because the baseline fails at every other
size.

| Criterion | Final result | Met |
| --- | --- | --- |
| Target: ≤ 150 MB per service | max 105 MB serial (950 MB file), 146 MB with 4 concurrent uploads | yes |
| Minimum: ≤ 25% of the file from 500 MB | 86 MB of 501 MB (17%), 105 MB of 952 MB (11%) | yes |
| Uploads up to 950 MB accepted | 15/15 serial, 12/12 concurrent (baseline 5/15, 0/12) | yes |
| Time ≤ +10% (100 MB) | 1.5 s against 2.0 s (−25%) | yes |

`img_storage` still grows slowly with the file size (59 → 77 → 100 MB median
from 100 to 950 MB), so the target holds for the tested sizes up to the 1 GiB
premium limit, not for arbitrary sizes.

## Effects on other quality attributes

- **Disk.** `projects` writes each upload to a temporary file
  (`UPLOAD_TMP_DIR`, default the container's `/tmp`), up to about 1 GB per
  upload and N GB with N simultaneous uploads. The file is removed once the
  response is sent, on success or error; a client that disconnects mid-upload
  left a partial file in `7590c4a`, which `870546b` fixed. In exchange, nginx no longer writes the request body to its own
  temporary file (`proxy_request_buffering off`).
- **Functional suitability.** Validation is unchanged and still happens
  before storing: `ffprobe` and `validateVideo` run on the temporary file,
  and only a valid video is sent to `img_storage`. All 19 regression checks
  pass.
- **Security and efficiency.** `api_gateway` now checks the JWT before
  reading the body; in the baseline the whole file was received first. A
  request whose `Content-Length` is already above the profile limit is refused
  by `projects` before any of the body is read.
- **Usability.** The import dialog shows upload progress. With nginx no longer
  buffering, the progress reflects the real transfer.
